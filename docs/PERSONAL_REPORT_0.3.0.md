# MacDPI 0.3.0 personal TUN report

The free personal build is implemented and packaged. Build 6 passed an owner-approved bounded GUI trial on the development Mac/network: Discord messaging/two-way voice, a real Roblox game and rejoining both services were owner-confirmed. Public HTTPS/API checks and Disable/restoration passed. The monitored enabled interval was about 25 min 44 s within the approved maximum 30-minute setup/test/shutdown window; exact 30-minute Active stability is not claimed. Earlier unauthenticated WSS and build 3 evidence remain separate. [Detailed timeline](TUN_VERIFICATION.md), [latest live record](verification/0.3.0-build6-live-personal.json).

Bounded copies are read as the requesting user into private root staging and checked against hashes embedded in the host. The helper authenticates the worker's UID and live audit-token code hash. In the earlier build 3 evening trial, the late independent snapshot encountered a **new owner-started session**. It therefore could not reproduce that disabled baseline for interfaces/capture policy. DNS, proxies, physical defaults, primary service and service order still matched. The old trial's engine/helper were gone. The new session survived a window close/reopen with the same engine/helper and was left enabled by the owner; the agent's monitor stopped. That historical snapshot does not prove full restoration. The subsequent build 6 trial independently verified all eight categories after Disable.

The normal application has no ten- or thirty-minute active-session timer. Those limits belonged to the authorized development trials, which the operator ended with Disable. Automatic setup cannot guarantee all sites or overcome encrypted/absent server names, every resolver policy or UDP-specific blocking. Extended daily reliability is still unverified. Developer ID signing/notarization and remote GitHub workflow execution are not complete; the repository and manual preparation workflow are ready for review, without an automatic publish step.

Build 6 retains the bounded, on-demand CPU/RSS display for the app and engine. It shows unavailable values when accounting fails and rejects results from a changed or stopped session. The root helper is excluded and disclosed, and no background resource polling is added. TCP/UDP/DNS algorithms are unchanged, while startup/cancellation and detach-verification lifecycle handling changed. A later approved build 6 activation and monitored interval passed with verified restoration. It was not an exact 30-minute Active test. The earlier [resource UI record](verification/0.3.0-resource-ui.json) is historical; [current hashes and checks](verification/0.3.0-release-readiness.json) cover build 6.

The prior [0.2.0 engineering report](FINAL_REPORT.md), build artifacts and local proxy path remain available. The MIT project includes separately licensed pinned Go/gVisor code in the personal worker; notices ship with the app. Build from reviewed source if macOS declines a downloaded ad hoc artifact. No Gatekeeper/SIP weakening, trust installation or system DNS/proxy/VPN rewrite is part of this workflow.

The late stop was observed only after it happened. Later protected-prefix hashes differ, which is consistent with one guard condition but does not prove causality. Neither root journal contents nor a retained reason establish why it stopped. Build 5 corrects the UI's overly specific helper attribution without pretending to fix that unknown trigger. [Late-stop record](verification/0.3.0-late-stop.json).

Build 6 writes only fixed caught-failure categories to the local macOS unified log. Worker logging is gated by the final failed outcome; normal stop/cancel is excluded. The helper startup branch accepts stop before readiness as cancellation, but this branch was compiled rather than directly executed with a real TUN. Known-lease detach verification has a local regression; native IPC tests cover the transport/release model, not a live helper startup. These changes and diagnostics do not retrospectively identify or fix the unexplained build 3 stop. A later manual read-only build 6 GUI check observed Disabled, Enable available, the inactive resource card with helper-excluded scope, Automatic setup selected and launch at login unchecked. The Settings text described Standard/System DNS with selective Cloudflare repair. That initial inspection changed no setting and requested no activation. A separate explicit approval later authorized the build 6 live trial; unlocking alone did not authorize it. No automated native UI suite was rerun.

The latest trial completed within its maximum 30-minute approved window, including setup and shutdown, with 1543.679 seconds of passive enabled monitoring. No unexpected stop was observed. All 26 public requests passed while active, and all eight baseline fingerprints plus the resolver matched after Disable. The owner confirmed application use and rejoining, but this remains one Mac/network and a bounded observation. The close-window/immediate-Active-window sequence does not establish prolonged hidden-window stability. Exact 30-minute Active, live crash/sleep/network/VPN transitions and other runtime combinations remain unverified; the older stop is still unexplained.
