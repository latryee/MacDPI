# MacDPI 0.3.0 personal TUN verification

The personal build contains a real userspace TCP/UDP engine and a separate, short-lived route helper. It uses a Darwin kernel control and ad hoc signatures. It needs no paid Apple Developer membership to build, and contains no Network Extension profiles or external DPI executable. The route helper needs the owner's per-session administrator authorization. The owner has now confirmed Discord bidirectional audio and a Roblox game session on this Mac/network. Broader compatibility and failure-transition testing remain preview work. [Build and trial procedure](PERSONAL_TUN.md), [current engineering report](PERSONAL_REPORT_0.3.0.md).

The safe tests surfaced two integration issues. The simulated datagram link needed enough packet queue capacity to model Darwin `utun` bursts. The native connected UDP sockets needed an explicit send buffer to forward the maximum datagram on this Mac, whose default was 9,216 bytes. TCP and UDP tests passed after those corrections. A four-flow synthetic UDP test sent 80 messages, received 72 replies and observed exactly the eight injected drops. Mean RTT was 0.280 ms and mean adjacent RTT variation was 0.125 ms. The earlier local HTTPS service evidence remains a separate, dated result. [Prior service validation](REAL_NETWORK_VALIDATION.md).

The earlier packaged worker awaiting authorization used 11.55 MiB RSS and no measurable CPU time over five seconds. The GUI used 89.09 MiB RSS with the local listener stopped and 95.19 MiB with it idle. The ten-second GUI samples measured 0.0% and 0.2% CPU respectively. Both the process sample and a five-second Instruments Time Profiler recording completed in the idle local mode. A later 496-second live TUN sample measured 0.41% combined app/engine/helper CPU and 130.33 MiB peak combined RSS with owner traffic. Strict enabled-idle CPU, physical latency/throughput, battery and 30-minute stability remain unmeasured. [Performance records](../PERFORMANCE.md).

## First live TUN smoke test

On 2026-11-06 at 22:50 Europe/Istanbul, the owner authorized one Terminal trial of the packaged 0.3.0 worker and helper, using the Standard profile and System DNS. The worker reported `CONFIGURING`, `ACTIVE`, `RESTORING` and `DISABLED` in that order. Certificate-verified HTTPS to example.com passed before activation, while active and after shutdown. The helper exited, and the primary service, physical defaults, interface list, protected prefixes, DNS, proxies, service order and network policy fingerprints all matched the baseline. The test ran the same packaged binaries as the app and drove them from a script. [Repeat the smoke test or use the app](PERSONAL_TUN.md#first-authorized-test).

The host had only a usable IPv4 physical default. The read-only plan contained 108 IPv4 capture prefixes and covered zero of one primary DNS addresses. That resolver stayed outside the tunnel. The same Mac later resolved three distinct public Discord names to the same single IPv4 address with system DNS. Direct requests to Discord's gateway API, download page and CDN then failed certificate verification. The system answer for discord.com did not overlap the Cloudflare IPv4 answers. A direct gateway API request using the Cloudflare answers without TLS splitting still failed during TLS setup with curl exit 35. The isolated Standard proxy with Cloudflare DoH returned the expected gateway API response with HTTP 200 and received an unauthenticated Gateway Hello over a certificate-verified WebSocket with HTTP 101. The smoke test did not cover LAN connectivity or authenticated desktop use. Discord and Roblox still require separate user-participated trials.

The optional `--discord` smoke probe compares one DoH address across the physical and captured TLS paths and separately records the System DNS result. Its parsing and route lookup passed isolated checks. It still requires an authorized live session. A temporary Dynamic Store resolver alone is insufficient for a safe scoped DNS implementation. Apple's IPMonitor can also append supplemental match suffixes to the default search list. That can send a previously local single-label lookup to an external resolver. [Apple resolver search list source](https://github.com/apple-oss-distributions/configd/blob/main/Plugins/IPMonitor/dns-configuration.c#L814-L861).

On 2026-11-07, a read-only lookup found a shared singleton public IPv4 address for each pair of Discord and Roblox probe names on this Mac. This satisfies the origin repair's trigger but does not prove poisoning on its own. Synthetic traffic demonstrated that the worker can dial a verified replacement address, split the initial record, preserve trailing bytes and return a response after TCP half-close. The Swift DNS bridge independently rejected unrelated TLS names, split-DNS names and private or mismatched DoH answers.

At 02:49 Europe/Istanbul on 2026-11-07, the owner authorized a live test of the packaged Standard engine with Cloudflare and TLS origin repair enabled. The public Discord gateway API returned its expected response through both the system-resolved address and a pinned DoH address, with certificate verification enabled. With the tunnel off, the system-address requests failed certificate verification (curl 60) and the pinned-address requests timed out (curl 28) both before and after the trial. Ordinary HTTPS passed at all three stages. The helper reported Disabled, both processes exited, and all eight network-policy fingerprints matched the pre-test baseline. The test did not compare the two TLS modes in separate active sessions, or exercise Discord authentication, voice or Roblox gameplay.

The owner subsequently reported reaching Discord and Roblox after activating with the original copied administrator command. This is user-reported access. The report did not establish bidirectional Discord audio or sustained Roblox gameplay.

The current synthetic repaired-TCP test injected a 60 ms encrypted lookup. The first connection took 61.83 ms and the next two took 0.38 and 0.39 ms, with one encrypted exchange across all three. Eight comparable steady-state synthetic UDP runs per version delivered 576 of 640 packets with exactly 64 deliberate drops in each version. The median of mean RTTs was 159.86 µs before the change and 160.65 µs after it. These results measure the repair's connection setup and local forwarding separately from Internet game or voice quality.

At 03:30 Europe/Istanbul on 2026-11-07, the owner authorized the automatic GUI trial. Enable displayed the macOS authorization request and then Active with Automatic setup. Certificate-verified ordinary HTTPS and Discord's public gateway API both passed while the public route used the new tunnel. Disable returned the app to Disabled. All eight network-policy fingerprints and the system resolver snapshot matched the baseline. Both TUN processes exited and no temporary root staging directory remained. Ordinary HTTPS passed again after Disable. This run used the app directly and required no pasted Terminal command.

The subsequent unprivileged mixed-load fixture exercised four TCP and four UDP flows concurrently for 15 seconds each over synthetic IPv4 and IPv6. Both families preserved 58.56 MiB of TCP payload in each direction and all 2,996 UDP replies; cancellation left zero worker flows. The full normal Go worker suite passed. A separate five-second-per-family mixed run and both families' injected-loss tests passed with the Go race detector and no race reports. The loss fixture previously failed under race instrumentation because a valid reply exceeded its 200 ms receive deadline. It now counts deliberate drops at the fixture and verifies subsequent reply identities instead of timing out on known drops. Resource and timing numbers include the simulated client stack and loopback peers; they do not verify physical TUN performance or voice/game quality. [Measurement scope, data and reproduction](../PERFORMANCE.md).

## Owner-participated voice and gameplay trial

On the evening of 2026-11-07 the owner approved a test lasting at most ten minutes. The first authorization attempt expired after 90 seconds without a broker. All policy and resolver fingerprints still matched, no engine/helper/script process remained and no root staging directory was left. The owner then enabled a new session and completed macOS authorization. The app reported Active, the public probe route used its tunnel, and ordinary HTTPS plus Discord's public API passed. An additional direct, certificate-verified Gateway connection returned HTTP 101 and a valid unauthenticated Hello. Three ordinary HTTPS request totals were 175–185 ms; these are completed HTTPS requests, not voice RTT. The kernel interface's sampled error/drop counters were zero, which does not measure worker queues or end-to-end voice loss.

The owner reported joining a Roblox game and remaining connected, and explicitly confirmed audio working in both directions in Discord. An initial page-loading complaint was clarified to refer to access after the operator ended the bounded trial with Disable; the owner confirmed normal operation while enabled. The agent did not inspect authenticated applications, credentials, microphone data or traffic contents.

The resource monitor captured 100 samples over 496.17 seconds. Combined CPU averaged 0.411% of one core; peak combined RSS was 130.33 MiB. Traffic was user-controlled, so this is neither a strict idle sample nor a battery or 30-minute stability benchmark. Disable visibly confirmed interface/route release and the old engine/helper exited. Before the independent after-snapshot finished, the owner started a new session. DNS, proxies, physical defaults, primary service and service order matched the baseline, while the new interface/capture policy made the other three fingerprints incomparable with a disabled baseline. Full eight-fingerprint restoration was verified in the earlier short GUI trial; it is not claimed for this last snapshot. The new owner-started session remained active with the same engine/helper across a window close/reopen action and was left enabled. The agent's resource monitor stopped. [Sanitized live evidence and exact limits](verification/0.3.0-live-personal.json).

Builds 4 and 5 were prepared after this live trial. They add on-demand CPU/RSS information for the host and its own engine, excluding the root helper explicitly. No route, TLS or UDP algorithm was changed. The full core suite passed 126 cases, and the hosted model suite passed 27. Both native resource self-reading and reading a bounded fixture child passed; canceled or changed sessions cannot restore stale UI measurements. Universal 2 app signatures and exact extracted ZIP/DMG content were verified. No new live activation is claimed for this build. [Recorded scope and hashes](verification/0.3.0-resource-ui.json).

During a later inspection, the owner-started build 3 session was no longer running. Its UI showed Failed with verified route cleanup; neither engine nor helper remained. Three subsequent read-only snapshots agreed and matched seven of the eight original disabled-baseline categories. Only protected-prefixes differed. Such a change is one health-check stop condition, but snapshots taken afterward cannot establish the trigger or its timing. The helper's sanitized stderr reason was not retained, and worker/IPC failures can also yield the same cleanup-confirmed status. Build 5 therefore describes the stop neutrally. This is an observed unexpected stop with verified cleanup, not a long-duration stability pass. [Sanitized follow-up and evidence limits](verification/0.3.0-late-stop.json).

## Build 6 release verification

Build 6 passed 130 Swift core, 27 hosted model and 14 packaging cases. The current Debug CLI freshly passed 23 loopback scenarios, and the native transport fixture passed four TCP/UDP IPv4/IPv6 scenarios. The full Go worker suite passed with 15-second mixed traffic per IP family, synthetic IPv4 96-TCP/64-UDP capacity bounds, UDP idle expiry, one-way empty-datagram activity and cancellation. Targeted UDP lifecycle race checks and native IPC also passed. These remain isolated tests, not WAN or installed lifecycle evidence.

Build 6 adds fixed-category local failure logging, gated so normal worker stop/cancel does not emit a failure category. Its helper branch treats stop before readiness as normal cancellation; that branch was compiled, not directly run with a real TUN. The known-lease detach regression was locally tested even without current ownership or a journal. TCP/UDP/DNS algorithms did not change; startup and cleanup lifecycle handling did. The unknown late build 3 stop is not claimed fixed.

Universal 2 signatures, exact extracted ZIP/DMG contents and post-promotion archive checksums were verified at `build/personal`. The prior resource UI record remains historical. The current interactive/UI check was unavailable because the Mac was locked; the three native UI cases are from an earlier run. No live build 6 activation or 30-minute stability test occurred, and nothing was published. [Current candidate hashes and release checks](verification/0.3.0-release-readiness.json).
