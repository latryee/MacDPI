# MacDPI 0.3.0 personal TUN verification

The personal build contains a real userspace TCP/UDP engine and a separate, short-lived route helper. It uses a Darwin kernel control and ad hoc signatures. It needs no paid Apple Developer membership to build, and contains no Network Extension profiles or external DPI executable. The route helper needs the owner's per-session administrator authorization. The product remains a preview until its installed lifecycle and native application use are verified. [Build and first trial](PERSONAL_TUN.md).

The safe tests surfaced two integration issues. The simulated datagram link needed enough packet queue capacity to model Darwin `utun` bursts. The native connected UDP sockets needed an explicit send buffer to forward the maximum datagram on this Mac, whose default was 9,216 bytes. TCP and UDP tests passed after those corrections. A four-flow synthetic UDP test sent 80 messages, received 72 replies and observed exactly the eight injected drops. Mean RTT was 0.280 ms and mean adjacent RTT variation was 0.125 ms. The earlier local HTTPS service evidence remains a separate, dated result. [Prior service validation](REAL_NETWORK_VALIDATION.md).

The final packaged worker awaiting authorization used 11.55 MiB RSS and no measurable CPU time over five seconds. The GUI used 89.09 MiB RSS with the local listener stopped and 95.19 MiB with it idle. The ten-second GUI samples measured 0.0% and 0.2% CPU respectively. Both the process sample and a five-second Instruments Time Profiler recording completed in the idle local mode. These are separate measurements. Combined app and helper memory, active TUN idle CPU, physical network latency and the 30-minute stability target require a live trial. [Performance records](../PERFORMANCE.md).

## First live TUN smoke test

On 2026-11-06 at 22:50 Europe/Istanbul, the owner authorized one Terminal trial of the packaged 0.3.0 worker and helper, using the Standard profile and System DNS. The worker reported `CONFIGURING`, `ACTIVE`, `RESTORING` and `DISABLED` in that order. Certificate-verified HTTPS to example.com passed before activation, while active and after shutdown. The helper exited, and the primary service, physical defaults, interface list, protected prefixes, DNS, proxies, service order and network policy fingerprints all matched the baseline. The test ran the same packaged binaries as the app and drove them from a script. [Repeat the smoke test or use the app](PERSONAL_TUN.md#first-authorized-test).

The host had only a usable IPv4 physical default. The read-only plan contained 108 IPv4 capture prefixes and covered zero of one primary DNS addresses. That resolver stayed outside the tunnel. The same Mac later resolved three distinct public Discord names to the same single IPv4 address with system DNS. Direct requests to Discord's gateway API, download page and CDN then failed certificate verification. The system answer for discord.com did not overlap the Cloudflare IPv4 answers. A direct gateway API request using the Cloudflare answers without TLS splitting still failed during TLS setup with curl exit 35. The isolated Standard proxy with Cloudflare DoH returned the expected gateway API response with HTTP 200 and received an unauthenticated Gateway Hello over a certificate-verified WebSocket with HTTP 101. The smoke test did not cover LAN connectivity or authenticated desktop use. Discord and Roblox still require separate user-participated trials.
